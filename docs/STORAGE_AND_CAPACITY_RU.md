# Хранилище и ёмкость Games Watchtower

Документ отвечает на два вопроса без предположений: **куда хаб реально записывает данные** и
**какую нагрузку он выдерживает**. Все числа получены исполняемыми проверками на этом репозитории
(см. §5 «Как воспроизвести»). Отдельно указано, что измерено, а что нет — «не измерено» здесь
означает именно «не измерено», а не «должно работать».

Дата замеров: 2026-09-27. Окружение: Node v22.22.3, Linux x86_64, 2 vCPU Intel Xeon @2.6 ГГц,
3.9 ГБ RAM, один процесс `server/index.js`, пустой inbox (если не сказано иное).

## 1. Что реально хранит данные

**Базы данных в проекте нет.** Ни PostgreSQL/TimescaleDB, ни SQLite, ни Redis, ни MongoDB:
в `package.json` нет ни одной runtime-зависимости (только `devDependencies`: `vite`, `jsdom`).
Проверка:

```bash
node -e "const p=require('./package.json'); console.log(p.dependencies||'dependencies: нет')"
grep -rn "sqlite\|postgres\|redis\|mongodb\|prisma\|sequelize" server/ src/ | grep -v "^server/modules" || echo "в исполняемом коде СУБД нет"
```

Упоминания PostgreSQL/TimescaleDB/Redis в `README.md`, `WATCHTOWER_OS_MASTER_PROMPTS.md`,
`PROJECT_PRODUCTION_READINESS_BRIEFS.md` — это **целевая архитектура и тексты промптов**, а не
реализация. Слои OS v3 отдают описания с `configured: false` (например `/api/indexer/config`,
`/api/storage/config`); они не подключаются к внешним сервисам.

| Данные | Где лежат | Переживают рестарт? | Ёмкость / лимит | Что происходит при переполнении |
|---|---|---|---|---|
| Нормализованные события игр (inbox) | Память процесса: `Map` в `server/ingestion/event-inbox.js` | **Нет** | `WATCHTOWER_MAX_EVENTS` (по умолчанию 250 000) + TTL `WATCHTOWER_EVENT_TTL_HOURS` (0 = выключен) | Вытесняются самые старые (счётчики `evictedByLimit`/`evictedByTtl` в `/api/ingestion/status` и `/metrics`); метрики считаются по остатку |
| Индекс идемпотентности (identity события) | Та же `Map` (ключи) | **Нет** | Совпадает с inbox | После рестарта повторно пришедшие события принимаются как новые |
| Лимиты частоты (rate limit buckets) | Память (`Map` в `server/security/access.js`) | **Нет** | 10 000 ключей | Старые ключи вычищаются; после рестарта счётчики с нуля |
| Журнал доступа (аудит) | Память (кольцо) | **Нет** | `WATCHTOWER_AUDIT_RING` (по умолчанию 1000) | Самые старые записи вытесняются; IP хранится как хеш |
| Сессии (`/api/session-keys/*`, симулятор) | Память | **Нет** | 10 000 сессий | Выдаёт `session_capacity_reached` |
| Заявки на контроль (`/api/control/requests`) | Память | **Нет** | — | Не персистентны: заявка исчезает после рестарта, исполнения нет и не было (`blockchainWrite: false`) |
| Курсоры приёма | `data/ingestion-cursors.json` (путь: `WATCHTOWER_CURSOR_FILE`) | **Да** | Размер файла | Атомарная запись (временный файл + `rename`) и очередь обновлений — `server/state/json-store.js` |
| Снимки инвесторских отчётов | `data/investor-snapshots.json` (`WATCHTOWER_SNAPSHOT_FILE`) | **Да** | 365 записей (старые вытесняются) | Атомарная запись и очередь; параллельные POST больше не теряют снимки |
| Отчёты аудита игр | `reports/*.json`, `reports/*.md` | **Да**, но только на чтение | — | Хаб их читает (`/api/ecosystem/*`), не пишет |

### Что это значит на практике

1. **Перезапуск пода = потеря всей истории.** После рестарта inbox пуст: все метрики честно
   возвращают `unavailable`/`null` (это проверяется: `npm run test:hardening`, тест про пустой inbox),
   но восстановить окно нельзя — данных за прошлое просто нет.
2. **Идемпотентность живёт ровно столько, сколько живёт процесс.** Повторная доставка события
   после рестарта создаст дубль метрик. Если события приходят из внешней очереди с at-least-once,
   нужен внешний dedup-стор (уникальный ключ события в БД).
3. **Переполнение inbox — это тихая потеря истории, видимая только в счётчиках.** Обязательные
   алерты: `watchtower_inbox_capacity_ratio > 0.8` и рост `watchtower_ingestion_evicted_total`.
4. **«Окно наблюдения» зависит от потока, а не от календаря.** 250 000 событий — это
   `250 000 / частота` секунд истории:

   | Частота событий | История в inbox (250 000 событий) |
   |---|---|
   | 10 событий/с | ~6,9 часа |
   | 100 событий/с | ~42 минуты |
   | 1 000 событий/с | ~4 минуты |
   | 48 000 событий/с (замеренный максимум приёма) | ~5 секунд |

   Поэтому в интерфейсе «DAU/7 дней» при живом потоке — это агрегат по последним доступным
   событиям, а не по семи суткам. Это не баг, но это надо знать до того, как числа пойдут инвестору.
5. **Один процесс — одна реплика.** Ни общего состояния, ни распределённой дедупликации,
   ни replay-кеша HMAC-подписей между репликами нет (см. `docs/OPERATIONS.md`, «Ограничения
   replay-защиты»). Горизонтальное масштабирование сейчас невозможно без внешнего хранилища.

## 2. Нагрузка: пропускная способность по маршрутам

Inbox пуст, `WATCHTOWER_RATE_LIMIT` поднят на время throughput-прогонов (иначе измерялся бы
лимитер, а не обработчик). `npm run load:full -- --scenario=read`.

| Маршрут | rps | p50 | p95 | Примечание |
|---|---|---|---|---|
| `GET /api/health` | 3 961 | 2,7 мс | 9,4 мс | публичный, самый дешёвый |
| `GET /api/events?limit=100` | 4 676 | 2,7 мс | 8,2 мс | чтение inbox + псевдонимизация |
| `GET /api/economy/overview` | 2 359 | 5,7 мс | 12,5 мс | 40 метрик по окну |
| `GET /api/read-model` (16 клиентов) | 1 318 | 10,5 мс | 21,9 мс | самый тяжёлый read: собирает все разделы |
| `POST /api/ingest/solana` (1 событие) | 2 722 | 6,7 мс | 17,7 мс | приём + валидация + дедуп |
| `POST /api/ingest/solana` (батч 200) | 296 запросов ≈ **59 000 событий/с** | 22,5 мс | 60,4 мс | рекомендованный режим приёма |
| `POST /api/ingest/solana` (батч 200, дубликаты) | 448 запросов ≈ **89 000 событий/с** | 14,8 мс | 33,9 мс | дедупликация дешевле записи |

Выводы по пропускной способности: приём событий не является узким местом — батчами хаб принимает
десятки тысяч событий в секунду, то есть на 4 игры и десятки тысяч игроков запаса хватает с
многократным превышением. Узкое место — **чтение при большом inbox**.

## 3. Деградация чтения от размера inbox (главный результат)

`GET /api/read-model` — тот маршрут, который открывает дашборд. Он считается синхронно, в том же
потоке, что и приём, и его стоимость линейна по числу событий в памяти.

| Событий в inbox | rps (8–16 клиентов) | p50 | p95 | Комментарий |
|---|---|---|---|---|
| 0 | 1 123 | 5,8 мс | 14,0 мс | базовый режим |
| 2 000 | 30,6 | 455 мс | 926 мс | падение в ~35 раз от пустого |
| 25 000 | 6,3 | 962 мс | 2 104 мс | дашборд неработоспособен |
| 100 000 | 2,5 | 2 399 мс | 5 118 мс | каждый запрос — секунды CPU |
| 250 000 (лимит по умолчанию) | 0 (обрыв) | — | — | запрос не укладывается в `headersTimeout = 15 с`, соединение сбрасывается (`ECONNRESET`) |

Один клиент (без конкуренции) при 250 000 событий: медиана **1 297 мс** на запрос, RSS 266 МБ.

Стоимость частей одного `read-model` при 30 000 событий (замер в процессе, `now` меняется —
как в HTTP-обработчике): `liveAggregates` ≈ 32 мс, `liveAlerts` ≈ 49 мс, `adjacent` ≈ 57 мс,
`investorReport` ≈ 47 мс, `economy` ≈ 9 мс, остальное ≈ 10 мс. То есть ~1,5 мс на 1 000 событий
на каждый агрегат, и агрегатов несколько.

### Соседние маршруты страдают вместе с аналитикой

При 250 000 событий и всего 4 клиентах на `/api/read-model` (замер `scripts/load-test.mjs`,
тот же процесс):

| Маршрут во время аналитической нагрузки | Латентность |
|---|---|
| `GET /api/health` (liveness) | 0,9–11 с |
| `POST /api/ingest/solana` (приём событий) | 6,5–11 с |

Причина одна: event loop занят синхронным расчётом, поэтому приём событий и health-check встают
в общую очередь. Практические следствия: (1) k8s/ECS liveness-проба с таймаутом 1–5 с начнёт
перезапускать контейнер под аналитической нагрузкой; (2) игры при отставании приёма упрутся в
таймауты своих отправок и начнут буферизовать события у себя.

### Память

| Событий | RSS |
|---|---|
| 0 | 66 МБ |
| 25 000 | 117 МБ |
| 100 000 | 202 МБ |
| 250 000 | 266 МБ |

≈ 1,06 КБ на событие в памяти. Лимит контейнера должен быть ≥ 512 МБ при дефолтных настройках
(иначе OOM-kill и полная потеря inbox).

## 4. Защитные лимиты как часть ёмкости

- `WATCHTOWER_RATE_LIMIT=120` (по умолчанию) — 120 запросов **в минуту на IP-адрес**, и лимит
  применяется ко всем маршрутам, включая статику и `/metrics`. Замер: 125 запросов к `/` дали
  119×`200` и 6×`429`. Значит один дашборд с десятком ресурсов расходует ~10 запросов на загрузку
  (≈12 загрузок в минуту), а Prometheus со скрейпом раз в 15 с — 4 запроса в минуту. Если за одним
  NAT/офисным IP сидят несколько операторов и скрейпер, лимит срабатывает раньше, чем кто-либо
  успевает работать. Для продакшн-нагрузки поднимайте лимит (максимум по конфигу — 100 000) и
  выносите `/metrics` за отдельный IP/allowlist.
- `WATCHTOWER_MAX_BODY_BYTES=65536` — 64 КБ на тело запроса: батч из 200 событий ≈ 40 КБ, поэтому
  размер батча привязан к этой переменной.
- `headersTimeout = 15 000` и `requestTimeout = 30 000` (`server/index.js`) — потолок времени
  обработки: всё, что дольше, обрывается. Именно это превращает «медленный» `read-model` при
  250 000 событий в «соединение сброшено».
- `app.maxRequestsPerSocket = 1000` — на одном keep-alive соединении; клиенты обязаны
  переподключаться (обычные HTTP-клиенты это делают).

## 5. Как воспроизвести замеры

```bash
# Кривая деградации чтения от размера inbox (25k/100k/250k)
node scripts/load-test.mjs --scenario=scale --concurrency=8 --duration=10 --max-preload=250000 \
  --json=reports/load-scale-local.json

# Пропускная способность: health, read-model, economy, events, приём, батч, дубликаты, mixed, лимитер
npm run load:full -- --scenario=all --concurrency=16 --duration=10 --json=reports/load-local.json

# Короткая проверка в CI (пороговые утверждения: без ошибок, p95 < 2 с)
npm run test:load
```

`--assert` включает пороговые утверждения. Они намеренно скромные: задача — ловить регрессию
порядка величины, а не различия между машинами. Абсолютные числа всегда пишутся в отчёт (`--json`).

## 6. Что ограничивает ёмкость и как это поднимать

| Предел | Сейчас | Как поднять |
|---|---|---|
| История событий | RAM одного процесса, 250 000 событий | PostgreSQL/TimescaleDB как источник правды + хаб как read-model поверх БД |
| Стоимость аналитики | Линейна по числу событий, синхронно в event loop | Инкрементальные агрегаты (пересчёт по дельте), материализованные представления в БД, кэш с инвалидацией по ревизии |
| Идемпотентность | В памяти процесса | Уникальный индекс `identity`/`event_id` в БД + `ON CONFLICT DO NOTHING` |
| Replay-защита HMAC | В памяти процесса | Общий атомарный nonce-store (Redis `SET NX`/таблица с TTL) |
| Несколько реплик | Не поддерживаются | Внешнее состояние + sticky-роутинг или шардирование по tenant |
| Наблюдаемость стоимости | `watchtower_http_request_duration_ms_max` | Отдельный экспортёр и бакеты по маршрутам |
| Аналитика и приём в одном потоке | Один процесс | Разделить на два процесса/сервиса (приём — отдельный, минимальный) |

**Рекомендуемый порядок работ перед реальной нагрузкой:**

1. Вынести события в PostgreSQL/TimescaleDB (не «когда-нибудь», а до первых боевых событий:
   сейчас любая перезагрузка стирает историю).
2. Ограничить аналитическое окно по времени и объёму (`LIMIT` по последним N событиям) и
   возвращать честный флаг `truncated: true` + `dataQuality`, чтобы числа не выглядели полными.
3. Разделить приём и аналитику на разные процессы: приём обязан оставаться быстрым всегда.
4. Общий dedup/nonce-стор для идемпотентности и HMAC-подписей.
5. Алерты: `watchtower_inbox_capacity_ratio`, `watchtower_ingestion_evicted_total`,
   `watchtower_http_request_duration_ms_max`, `watchtower_last_event_age_seconds`.
6. Нагрузочный прогон (`npm run load:full`) — в приёмочный чек-лист каждого релиза.

## 7. Что уже улучшено в этом репозитории (2026-09-27)

- **Мемоизация аналитики внутри состояния inbox** (`server/analytics/live-model.js`): один запрос
  `/api/read-model` пересчитывал `liveAggregates` до десяти раз; теперь результат считается один
  раз и ключ включает ревизию inbox (`inboxRevision()`), поэтому устаревшие числа вернуть
  невозможно. Замер: при 30 000 событиях один `read-model` — 55,9 мс вместо ~481 мс (сумма частей
  до правки); при 2 000 событиях в HTTP-прогоне p50 упал с 724 мс до 455 мс.
- **Атомарная запись файлов состояния** (`server/state/json-store.js`): временный файл + `rename` +
  `fsync`, очередь на файл. Тесты: `npm run test:state` (параллельные `setCursor` и снимки больше
  не теряются, обрезанный JSON не роняет чтение).
- **Нагрузочный тест** (`scripts/load-test.mjs`, `npm run test:load`) и **пороговые утверждения**
  в CI: первая в репозитории проверка производительности, а не только корректности.
- **Проверка границ агентной безопасности** (`npm run test:agent-safety`) — пункты 71–82
  каталога угроз; подробности в `docs/SECURITY_CONTROL_COVERAGE_RU.md`.
- Тестовый сервер теперь **падает с понятной ошибкой**, если не поднялся за 15 с, вместо молчаливой
  отдачи мёртвого порта (раньше ошибка конфигурации выглядела как `ECONNREFUSED` в тестах).

**Что этим не решено:** стоимость аналитики остаётся линейной по числу событий, история остаётся
в памяти и теряется при рестарте; при inbox 250 000 событий `/api/read-model` по-прежнему
нежизнеспособен. Это ограничение архитектуры, и оно снимается только внешней БД (§6).
