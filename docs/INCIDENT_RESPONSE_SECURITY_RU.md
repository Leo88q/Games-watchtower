# Реагирование на security-инцидент Watchtower и интеграций

Это технический runbook для оператора; он не даёт полномочий замораживать средства, менять владельцев программ, отзывать внешние multisig-ключи, уведомлять регуляторов или делать юридические выводы. Такие решения принимают уполномоченные люди по утверждённым процедурам. Не вставляйте секреты, seed phrase, приватные ключи или полные токены в тикеты, логи, чат и этот репозиторий.

## Триаж и эскалация

1. **Подтвердить сигнал независимым способом.** Сопоставить время/slot/signature и состояние аккаунтов как минимум с независимым RPC или доверенным explorer. Watchtower использует аналитический read-model; единичный RPC/ingest-сигнал, метрика цены или `confirmed`-событие не являются доказательством финальности, взлома или права на выплату.
2. **Ограничить воздействие в пределах полномочий.** При подозрении на компрометацию API отключить доступ к соответствующему ingress/route на доверенном gateway либо остановить сервис; не переключать его на открытый режим и не удалять доказательства. При угрозе кошельку/игровой программе срочно эскалировать владельцам соответствующего signer, multisig и программы: этот репозиторий не имеет технической возможности отозвать их полномочия или остановить транзакции.
3. **Сохранить минимум доказательств.** Зафиксировать UTC-время, версии релиза/образа и commit, идентификаторы запросов, HTTP-статусы, sanitized audit entries, RPC-провайдер/commitment и известные signature/slot. Перед передачей проверить, что журналы не содержат bearer-токенов, HMAC, адресов игроков сверх необходимого или содержимого секретов. Не собирать лишние персональные данные.
4. **Сменить затронутые секреты через секрет-хранилище.** Составить список только имён переменных/ключей (без значений), выпустить новые credentials, обновить отправителей и сервис, проверить отказ старых, удалить старые значения из runtime/CI и проверить историю логов. Если мог утечь wallet/KMS/signing key — это отдельный инцидент владельца ключа: действовать по его заранее утверждённому quorum/rotation plan, никогда не пересылать ключ в Watchtower.
5. **Проверить целостность поставки.** Сверить deployed image digest и Git commit с одобренным release; при подозрении на пакет/Action отключить автоматические deploys, сохранить lockfile и provenance, проверить diff и CI-логи с маскированным выводом. Не выполнять неизвестный скрипт «для диагностики» на workstation с доступом к ключам.
6. **Восстановить из проверенного источника.** Развернуть чистый reviewed commit/image, проверить `/api/health` (`writes: false`), `/api/readyz`, auth/ingest rejection и отсутствие секретных файлов/внутренних путей в публичной статики. Возобновлять интеграции постепенно, сверяя данные и freshness.
7. **Пост-инцидентный review.** Уполномоченная команда классифицирует воздействие, уведомления/юридические обязанности и допустимость повторного запуска; добавить regression-тест, обновить coverage с доказательством и назначить дату повторного аудита. Не считать закрытие тикета доказательством устранения первопричины.

## Ротации без значений

Для Watchtower проверить необходимость ротации: `WATCHTOWER_INGEST_TOKEN`, `WATCHTOWER_INGEST_HMAC_SECRET`, `WATCHTOWER_READ_TOKEN`, `WATCHTOWER_PII_SALT`, CI/deploy credentials и внешних provider tokens. Для внешней игры отдельно проверить signer/KMS keys, wallet/session keys, multisig membership, upgrade authority и RPC/API credentials. Значения сюда не записывать. `WATCHTOWER_PII_SALT` меняет псевдонимы; перед ротацией согласовать пересчёт зависимых snapshots/дашбордов.

## Ограничения доказательств

- Процессный HMAC replay-cache и session map локальны одному процессу; они не заменяют общий атомарный store в многорепличном деплое.
- `server/contracts/` — непроверенные Anchor-спецификации, не deployed program и не действующий emergency control.
- Session-key API — policy simulation; его успешный ответ не означает подпись или on-chain authorization.
- Dashboard prices, `confirmed` events и ответы одного RPC не являются settlement oracle или независимым quorum.
