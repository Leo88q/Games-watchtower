# Чек-лист безопасности крипто-игр на Solana / Anchor

Сводный документ для аудита экономики и смарт-контрактов крипто-игр на Solana. Формат каждого пункта: **уязвимость → фикс**, при наличии — реальный прецедент.

> **Важно:** чек-лист не заменяет независимый аудит и не является гарантией безопасности. Примеры инцидентов, суммы и даты ниже приведены по указанным источникам и перед внешней публикацией должны быть перепроверены по первичным постмортемам. Учитывайте версию Anchor, Solana runtime и используемых Token Program.

## Часть 0 — базовый аудит (пункты 1–30)

### A. Идентичность и аккаунты

1. [ ] **Отсутствие PDA-seeds/bump** → произвольная инициализация аккаунта. **Фикс:** `seeds`, `bump`, `init`, точный `space`.
2. [ ] **Отсутствие `has_one` для mint/authority** → можно подставить чужой токен. **Фикс:** `has_one = mint`, `owner = player`.
3. [ ] **Отсутствие `signer` у плательщика** → за операцию может заплатить кто угодно. **Фикс:** `#[account(mut, signer)]`.
4. [ ] **Нет проверки `system_program`** → CPI может быть направлен в поддельную системную программу. **Фикс:** `#[account(address = system_program::ID)]`.
5. [ ] **Нет rent-exemption** → аккаунт может быть закрыт при нехватке средств на аренду. **Фикс:** проверка `rent.minimum_balance(space)` или использование корректного механизма инициализации Anchor.
6. [ ] **Неинициализированное нулевое состояние трактуется как валидное**. **Фикс:** явная инициализация (`init_space`) и зануление/проверка полей состояния.

### B. Состояние и реентрантность

7. [ ] **CPI во внешнюю программу до фиксации состояния** → повторный вход или взаимодействие со старым состоянием. **Фикс:** обновлять состояние до CPI там, где это безопасно, применять guard/lock-паттерн и проверять необходимые права аккаунтов.
8. [ ] **Self-CPI без проверки дискриминатора** → рекурсия или нежелательное повторное выполнение. **Фикс:** проверять вызываемую инструкцию через `sysvar::instructions`, ограничивать допустимые CPI и глубину вызова.
9. [ ] **Устаревшие закэшированные значения вместо чтения состояния аккаунта** → расчёт использует неактуальные данные. **Фикс:** не полагаться на глобальный кэш либо использовать версионирование и проверку актуальности.
10. [ ] **Излишнее доверие `Clock`/slot в критичной логике** → значение или исход игры можно предсказать/манипулировать в допустимых пределах. **Фикс:** применять slot только для временных окон и экспирации, не использовать его как источник случайности или цен.

### C. Токеномика и экономика

11. [ ] **Mint authority не отозван** → возможен неограниченный минт. **Фикс:** проверять `mint_authority.is_none()` и `freeze_authority.is_none()`, если модель токена требует их отзыва.
12. [ ] **Token extensions (например, transfer fee) не учтены** → фактически полученная сумма отличается от расчётной. **Фикс:** явно проверять расширения mint и учитывать их семантику.
13. [ ] **Overflow в расчёте комиссии**. **Фикс:** `checked_mul` и проверка границ результата.
14. [ ] **Underflow баланса**. **Фикс:** использовать `checked_sub` и явно обрабатывать ошибку.
15. [ ] **Округление комиссии в пользу атакующего** → систематическая потеря средств или обход комиссии. **Фикс:** задать инвариант `fee <= amount`, явно выбрать floor/ceil и покрыть граничные значения тестами.
16. [ ] **Treasury не PDA или доступен админу напрямую** → средства можно вывести в обход правил программы. **Фикс:** treasury-PDA и выплаты только через проверенные программные инструкции.
17. [ ] **Фронтраннинг/MEV на публичных изменениях состояния** → выгодное действие перехватывается или повторяется. **Фикс:** commit-reveal, nonce, ограниченное slot-окно и проверка ожидаемого состояния.
18. [ ] **DoS через неограниченные циклы по игрокам** → исчерпание compute budget. **Фикс:** лимиты размера массивов и пагинация.
19. [ ] **Спам логов/событий** → лишняя нагрузка и рост затрат на обработку. **Фикс:** `emit!` только для необходимых критичных событий.
20. [ ] **«Бог-режим» админа без ограничений** → привилегированный ключ может единолично изменить экономику или вывести средства. **Фикс:** timelock, multisig и неизменяемые после генезиса параметры, где это возможно.

### D. Anchor-специфика

21. [ ] **Неверный `space = 8 + ...`** → нехватка места или некорректная раскладка аккаунта. **Фикс:** точный расчёт размера либо `#[derive(InitSpace)]`.
22. [ ] **`#[account(init)]` без payer/system_program** → инициализация не имеет корректного плательщика или системной программы. **Фикс:** задавать и валидировать `payer` и `system_program`.
23. [ ] **Лишний `#[account(mut)]` на read-only аккаунтах** → ненужная изменяемость и расширение поверхности атаки. **Фикс:** помечать аккаунт `mut` только когда он действительно изменяется.
24. [ ] **Untrusted-данные десериализуются без версии** → совместимая на вид структура может интерпретироваться неверно. **Фикс:** проверять версию при `try_deserialize` и отклонять неподдерживаемые форматы.
25. [ ] **Коллизия дискриминаторов при кастомных инструкциях** → инструкция может быть обработана не тем путём. **Фикс:** проверять уникальность дискриминаторов и корректность сериализации.
26. [ ] **Рассинхрон IDL/индекса инструкции при апдейте** → клиент вызывает не ту инструкцию или передаёт неверные аккаунты. **Фикс:** версионировать IDL и проверять совместимость клиента и программы в CI.

### E. Solana runtime

27. [ ] **Истощение compute budget** → транзакция не выполняется или используется для DoS. **Фикс:** задавать обоснованный `set_compute_unit_limit`, ограничивать работу и избегать тяжёлых аллокаций.
28. [ ] **Rent-refund при `close` уходит не туда** → арендный остаток получает неверный адресат. **Фикс:** закрывать аккаунт только с возвратом владельцу или проверенному treasury-PDA.
29. [ ] **Дублирующиеся аккаунты в одной инструкции** → одна и та же учётная запись используется в нескольких ролях вопреки ожидаемым инвариантам. **Фикс:** проверять уникальность ключей там, где роли должны быть различными.
30. [ ] **Фичагейты/устаревшие sysvar** → поведение отличается между окружениями или после обновления runtime. **Фикс:** фиксировать версии зависимостей и проверять программу на целевом runtime и актуальных sysvar.

## Часть 1 — техническое дополнение по Anchor/Solana (пункты 31–54)

### F. Идентичность и доверие к CPI

31. [ ] **Нет owner-check на «сырых» `AccountInfo`** (не обёрнутых в `Account<'info, T>`) → данные чужого аккаунта интерпретируются как свои. **Фикс:** использовать типизированные аккаунты либо вручную проверять `owner == program_id` до чтения данных.
32. [ ] **Program ID CPI-таргета не проверяется явно** → атакующий может подставить другую программу вместо ожидаемой. **Фикс:** ограничивать адрес, например `#[account(address = token::ID)]` или соответствующим ID ожидаемой программы.
33. [ ] **Token account не является канонической ATA получателя** → выплата может уйти на нецелевой аккаунт. **Фикс:** валидировать `associated_token::authority` и `associated_token::mint`.
34. [ ] **«Revival»-атака: ручной `close` без зануления данных** → аккаунт может быть повторно инициализирован в той же транзакции. **Фикс:** использовать проверенный `#[account(close = ...)]` и корректно закрывать состояние; не полагаться на ручное изменение lamports.
35. [ ] **Type confusion между структурами одинакового `space`** → данные одного типа читаются как другой. **Фикс:** не отключать автогенерируемый Anchor-дискриминатор и валидировать тип аккаунта.

### G. Честность рандома

36. [ ] **RNG на blockhash/slot/timestamp** → результат предсказуем и допускает повтор попытки. **Фикс:** использовать проверяемый VRF (например, Switchboard/ORAO) либо commit-reveal с задержкой не менее одного слота и защитой от отказа раскрыть секрет.
37. [ ] **Нет one-shot защиты на розыгрыш** → игрок может повторять попытки до желаемого результата. **Фикс:** выставлять PDA-флаг «уже использовано» до раскрытия результата и обеспечивать одноразовость.

### H. Token-2022 и продвинутые токен-риски

38. [ ] **Transfer Hook extension** → при CPI-переводе токена вызывается сторонняя hook-программа с дополнительной логикой. **Фикс:** проверять mint и whitelist допустимых hook-программ; учитывать все требуемые hook-аккаунты.
39. [ ] **Permanent Delegate / Default Frozen State** → токен может быть списан делегатом или аккаунты могут создаваться замороженными. **Фикс:** проверять расширения mint перед тем, как принимать токен в игровую экономику.
40. [ ] **Несовпадение decimals при конвертации lamports/токенов/очков** → некорректные суммы, округления или арбитраж. **Фикс:** единая константа decimals, явные единицы измерения и unit-тесты конверсий.

### I. Офчейн ↔ ончейн

41. [ ] **Подпись бэкенда на одобрение действия без nonce/expiry** → возможны replay и повторная выплата. **Фикс:** одноразовый nonce, срок действия и PDA-флаг `claimed`.
42. [ ] **Инструкции не защищены от «sandwich» в той же транзакции** → порядок инструкций может изменить проверяемые предпосылки. **Фикс:** при необходимости проверять последовательность через `sysvar::instructions` и валидировать весь допустимый контекст транзакции.
43. [ ] **Hot-wallet бэкенда с чрезмерными полномочиями** → компрометация ключа позволяет вывести значительные средства. **Фикс:** лимитировать баланс, ротировать ключи и использовать multisig для пополнения/крупных переводов.

### J. Апгрейд программы и операционка деплоя

44. [ ] **Upgrade authority — обычный keypair без timelock/multisig** → единственный ключ может незаметно заменить программу. **Фикс:** Squads multisig/timelock либо отзыв upgrade authority после стабилизации, если дальнейшие апдейты не нужны.
45. [ ] **Деплой без reproducible build** → опубликованный бинарник нельзя надёжно сопоставить с исходниками. **Фикс:** `anchor verify` / Solana Verified Build и воспроизводимая сборка в CI.

### K. NFT и игровые предметы

46. [ ] **Update authority метаданных NFT остаётся у одного кошелька после минта** → метаданные могут быть изменены централизованно. **Фикс:** передавать полномочия в контролируемую multisig-схему или отзывать authority после финализации коллекции (burn authority относится к праву сжигания и не заменяет update authority).
47. [ ] **Delegate/approve на NFT (аренда/стейкинг) не отзывается автоматически** → делегат сохраняет доступ после возврата предмета. **Фикс:** отзывать делегирование (`revoke`) в той же инструкции, что и возврат.

### L. Экономический античит на уровне геймдизайна

48. [ ] **Sybil-фарминг рефералов/квестов множеством кошельков** → награды извлекаются без реальных уникальных игроков. **Фикс:** верификация при клейме, rate-limit и ступенчатые пороги наград.
49. [ ] **Нет инварианта «сумма балансов игроков + treasury = total supply»** → незаметная эмиссия или потеря средств. **Фикс:** мониторить инвариант после каждой значимой операции и разбирать расхождения.

### M. Клиент и кошелёк игрока

50. [ ] **Wallet-drainer через фишинговый UI или скомпрометированную npm-зависимость в билде** → игрок подписывает вредоносную транзакцию. **Фикс:** CSP, pin версий, lock-файлы и `npm audit`/сканирование зависимостей в CI.
51. [ ] **Подпись транзакции без симуляции и понятного превью** → пользователь не понимает, какие активы и полномочия передаёт. **Фикс:** `simulateTransaction` и человекочитаемое превью на основе IDL до подписи.

### N. Тесты

52. [ ] **Нет fuzz/property-based тестов инструкций** → граничные сочетания аккаунтов и входов остаются непроверенными. **Фикс:** применять fuzz/property-based тестирование (например, Trident для Anchor), а не только happy-path тесты.
53. [ ] **Нет инвариантных тестов** → `total_supply`, `treasury_balance` и сумма балансов могут расходиться. **Фикс:** проверять инварианты после каждой инструкции в тестах.
54. [ ] **Нет экономической симуляции** → эксплойты, возникающие только после длительной серии действий, остаются незамеченными. **Фикс:** симулировать тысячи игровых сессий с предельными, но допустимыми действиями.

## Часть 2 — нетривиальные и экономические атаки (пункты 55–70)

### O. Гонки состояний и дублирование (особенно опасно для farm-игр)

55. [ ] **Race condition в оффчейн-части маркетплейса/бэкенда** — параллельные запросы на покупку/клейм до фиксации баланса могут задвоить выплату. **Прецедент:** Aurory SyncSpace (декабрь 2023): по сообщениям, шквал параллельных запросов раздул оффчейн-баланс AURY, после чего было выведено около 600 тыс. токенов; аудит смартконтракта прошёл успешно, поскольку уязвимость находилась в бэкенд-логике гибридной онлайн/офлайн инвентарной системы. **Фикс:** атомарные транзакции/optimistic locking в БД, идемпотентные запросы с уникальным request ID и серверный mutex на игрока.
56. [ ] **Классический item-duplication баг farm-игры** — параллельные/повторные вызовы harvest/craft до записи состояния выдают ресурс дважды. **Прецедент:** оригинальная Sunflower Farmers (Polygon) — баг дублирования привёл к бот-шторму, нарушившему работу игры и перегрузившему сеть. **Фикс:** строгая блокировка состояния игрока при harvest/craft, идемпотентность инструкций (nonce/slot) и отказ от предположения, что оптимистическая параллельность безопасна.
57. [ ] **Инъекция результата в оффчейн-скоринг** (лидерборды, PvP, турниры) — очки считаются на клиенте/в незащищённом API и без проверки отправляются в контракт. **Прецедент:** в описаниях инцидента Manarium сообщалось, что исследователи подставляли произвольный winning score в бэкенд без игры и забирали призовой пул. **Фикс:** сервер — единственный источник истины; подписывать каждый результат с nonce; клиент не должен передавать итоговый счёт как доверенный факт.

### P. Токеномика и деградация экономики

58. [ ] **«Фейковый бёрн»** — механика «потрать X, получи X+ в награду» выглядит дефляционной, но создаёт чистую эмиссию. **Прецедент:** экономика StepN (GMT/GST) часто приводится как пример зависимости burn-механик ремонта/апгрейда от притока новых игроков; такие механики не гарантируют устойчивость токена. **Фикс:** до запуска моделировать чистый эмиссионный баланс (эмиссия минус сжигание) при разных сценариях поведения, включая стрессовые, а не только «средние».
59. [ ] **Спуфинг активности/входных данных, подтверждающих честную игру** — боты имитируют реальные действия. Для task-маркетплейса аналог — массовая отправка низкокачественных или похожих AI-клипов ради фарма SKR. **Фикс:** антифрод-эвристики по частоте и паттернам отправки, similarity-detection между клипами связанных кошельков и проверка качества/человеческого участия при клейме.
60. [ ] **Флэш-лоан или внутритранзакционная манипуляция кастомной кривой ценообразования** — последовательность депозит → действие → вывод в одной транзакции искажает курс. **Прецеденты:** Nirvana Finance (манипуляция bonding curve с использованием flash loan), Crema Finance (поддельный tick-аккаунт и flash loan), Solvent SVT (flash loan и повторные сделки для сдвига цены). На Solana классический flash loan встречается иначе, чем на EVM, но риск атомарной манипуляции остаётся. **Фикс:** TWAP вместо спотовой цены, лимит изменения цены за транзакцию/блок и анализ всех доступных атомарных последовательностей.
61. [ ] **Wash-trading на внутриигровом NFT-маркетплейсе** искусственно поднимает floor price ресурсов, который может повлиять на расчёты крафта или залога. **Фикс:** выявлять сделки между связанными кошельками и не использовать floor price маркетплейса как единственный источник истины для игровой механики.

### Q. Governance и организационные риски

62. [ ] **Захват «спящего» DAO спамом предложений** — множество безобидных предложений скрывает вредоносное, а кворум набирается токенами инициатора. **Прецедент:** Synthetify DAO (октябрь 2023) — по опубликованному разбору, атака привела к выводу около $230 тыс. **Фикс:** veto-совет/multisig поверх голосования и уведомления о новых предложениях.
63. [ ] **Multisig с низким порогом** — схема 1-из-N фактически эквивалентна одному приватному ключу. **Прецедент:** Saga DAO (январь 2024) — обсуждался инцидент с порогом 1/12 и обвинениями в insider theft. **Фикс:** для казначейства — порог не ниже 3–5 из N в соответствии с моделью угроз; ключи физически и организационно разделены между держателями.
64. [ ] **Инсайдерская угроза с привилегированным доступом** — сотрудник/контрибьютор злоупотребляет правами. **Прецеденты:** Pump.fun — бывший сотрудник использовал withdrawal authority в атаке с flash loan на сумму около $1,9 млн; Cypher Protocol — core-контрибьютор похитил около $317 тыс. из фонда компенсаций. **Фикс:** принцип наименьших привилегий, отзыв доступа и ротация ключей при увольнении, разделение обязанностей — один человек не должен единолично одобрять и исполнять перевод.

### R. Инфраструктура и supply chain

65. [ ] **Утечка приватных ключей через сторонний сервис/логирование бэкенда**. **Прецеденты:** утечка seed-фраз из Slope Wallet через сервер логирования; DEXX — приватные ключи в открытом виде на сервере экспорта и заявленные потери около $30 млн; Thunder Terminal и Solareum — компрометация через строку подключения MongoDB. **Фикс:** никогда не логировать и не хранить приватные ключи/seed-фразы в открытом виде; использовать KMS/HSM и исключать секреты из диагностических данных.
66. [ ] **Supply-chain-компрометация npm/JS-зависимостей фронтенда или бота**. **Прецедент:** опубликованные версии `@solana/web3.js` 1.95.6/1.95.7 были скомпрометированы через учётную запись публикующего в декабре 2024 года. **Фикс:** точные версии и lock-файлы, проверка происхождения артефактов, `npm audit` и сканирование зависимостей в CI.
67. [ ] **DNS-hijack фронтенда игры** → подмена домена направляет игроков на фишинговую копию. **Прецедент:** сообщалось об инциденте с Parcl в августе 2024 года. **Фикс:** DNSSEC, мониторинг изменений DNS/сертификатов и 2FA с аппаратным ключом для аккаунта регистратора.

### S. Дополнительно: Anchor-специфика

68. [ ] **Storage/layout аккаунта ломается при апгрейде программы** — после изменения структуры `Player`/`Treasury` старые аккаунты десериализуются некорректно. **Фикс:** поле `version` в структуре аккаунта, явные миграционные инструкции и тестирование апгрейда на форке мейннета с репрезентативными старыми аккаунтами.
69. [ ] **Батчевые операции без поэлементной авторизации** — массовый airdrop/mint проверяет права один раз на всю пачку, а не для каждого элемента. **Фикс:** независимо проверять авторизацию, получателя и лимиты для каждого элемента батча.
70. [ ] **Крафт уязвим к неатомарности** — списание ресурсов и выдача предмета выполняются раздельно, что позволяет получить предмет без полной оплаты. **Фикс:** списание ресурсов и выдачу предмета выполнять в одной атомарной инструкции/транзакции с проверкой результата всех CPI.

## Часть 3 — угрозы 2026 года: ИИ-агенты и отравление аудита (пункты 71–82)

Это направление актуально в двух случаях: если ИИ-инструмент «Soup» (или любой другой бот) получает доступ к кошельку/инструментам как «оракул» или разработчик; и если независимый ИИ-аудит (Watchtower) используется для проверки контрактов. Сам процесс аудита — отдельная поверхность атаки.

### T. Агентные ИИ-кошельки и автономное исполнение

71. [ ] **Indirect prompt injection против ИИ-агента с доступом к кошельку** — вредоносная инструкция находится не в прямом запросе пользователя, а во внешнем содержимом, которое ИИ читает в обычной работе (пост, страница, RPC-ответ, файл). **Прецедент:** в описании инцидента мая 2026 года атакующий отправил сообщение азбукой Морзе в публичный тред с ИИ-агентом Grok; агент декодировал текстовую команду и передал её торговому боту Bankrbot, который без участия человека подписал и отправил, по сообщениям, $150–200 тыс. **Фикс:** считать весь внешний текст враждебным; агент, который читает данные, физически не должен быть тем же агентом, который подписывает транзакции.
72. [ ] **Владение токеном/NFT ошибочно принимается за аутентификацию** — перевод NFT атакующим может автоматически повысить права кошелька. **Прецедент:** это описывалось как часть упомянутого инцидента с Grok/Bankrbot. **Фикс:** владение NFT/токеном — только сигнал, не аутентификация; право, которое может выдать действие атакующего, не является надёжным контролем доступа.
73. [ ] **Межагентное доверие без повторной аутентификации («confused deputy» для ИИ)** — один агент без проверки исполняет то, что декодировал или сообщил другой. **Фикс:** повторно аутентифицировать каждое действие на границе между агентами; вывод ИИ никогда не считать прямой командой человека.
74. [ ] **Отравление персистентной памяти ИИ-агента (memory injection)** — поддельная запись, внедрённая через один канал, срабатывает позже через другой. **Прецедент:** для фреймворка ElizaOS (ранее ai16z) описывалась уязвимость этого класса; указанный объём активов требует проверки по первоисточнику. **Фикс:** криптографическая аутентификация каждой записи памяти (например, HMAC с управлением ключом), контроль источника/целостности и запрет исполнять сохранённые инструкции без подтверждения.
75. [ ] **Нет человека в цепочке для операций с реальной ценностью** — ИИ может двигать средства или менять параметры экономики без approval-порога, лимитов и allowlist получателей. **Фикс:** лимиты и allowlist должны обеспечиваться инфраструктурой/смарт-контрактом, а не промптом; значимые операции требуют подтверждения человека.

### U. Отравление самого процесса аудита

76. [ ] **Скрытая инструкция в README/комментариях кода обманывает ИИ-аудитора** — невидимый Unicode, zero-width-символы или текст вроде «функция вне скоупа, контроль доступа реализован оффчейн» могут побудить модель умолчать об уязвимости. **Прецеденты близкого класса:** CurXecute CVE-2025-54135 и Kilo Code CVE-2025-11445 — скрытые инструкции в README/issue влияли на поведение ИИ-ассистентов. **Фикс:** выявлять невидимые символы перед аудитом; проводить отдельный проход по чистому коду без README/комментариев; не принимать от самого ассистента фразу «вне скоупа» как основание пропустить проверку.
77. [ ] **Auto-approve файловых операций агентных coding-инструментов** — скрытая инструкция в данных может побудить ассистента изменить конфигурацию/код и отправить бэкдор. **Фикс:** ручное подтверждение записей в конфигурацию и код отдельно от обычного code review; ограниченные права инструмента и проверка diff.

### V. MCP и инструментарий агентов

78. [ ] **Tool poisoning** — вредоносная инструкция спрятана в описании (docstring) инструмента/MCP-сервера, который вызывает ИИ. **Фикс:** не подключать непроверенные MCP-серверы к агенту с доступом к ценным операциям; фиксировать хэш описания инструмента при регистрации и сверять его при каждом вызове, чтобы обнаруживать незаметную подмену («rug pull»).
79. [ ] **Компрометация роутера/прослойки между агентом и моделью** — инфраструктура, пересылающая запросы к LLM, может подмешивать вызовы инструментов или выводить учётные данные. **Фикс:** минимально необходимые права у любого MCP-сервера/роутера; read-only по умолчанию, аудит трафика и изоляция секретов.

### W. Общее давление ИИ на скорость и масштаб атак

80. [ ] **Автономные ИИ-агенты ускоряют поиск и эксплуатацию уязвимостей** — промежуток между публикацией класса уязвимости и эксплуатацией может сократиться до часов. **Прецедент:** описывался случай, когда агент без участия человека в реальном времени прошёл несколько шагов повышения привилегий и извлёк базу данных через публичный dev-инструмент менее чем за час. **Фикс:** рассматривать аудит-промпт Watchtower как непрерывный процесс для каждого коммита, а публичные dev/admin-инструменты размещать за VPN/allowlist.
81. [ ] **AI-бренд как приманка для дрейнеров, направленных на игроков** — мошеннический контент про «ИИ-бота для арбитража» убеждает жертву самой задеплоить и профинансировать контракт-пересыльщик на кошелёк мошенника. **Фикс:** в обучающем/промо-контенте явно указывать, что официальные контракты публикуются только по адресам с официального сайта; никогда не просить игроков самостоятельно деплоить что-либо «ради заработка».

### Бонус: durable nonce и социальная инженерия multisig

82. [ ] **Оружейное использование durable nonce и социальная инженерия подписантов multisig** — заранее подписанная durable-nonce-транзакция не истекает как обычная транзакция с recent blockhash, поэтому её могут исполнить позднее в ином контексте. **Прецедент:** по сообщениям об инциденте Drift Protocol 1 апреля 2026 года, атакующие похитили около $285–286 млн: двух из пяти подписантов убедили заранее подписать durable-nonce-транзакции; параллельно был создан фиктивный токен, его цена манипулировалась через wash-trading, а при смене Security Council использовался zero-timelock. Атака заняла около 12 минут. **Фикс:** проверять durable-nonce-транзакцию с той же строгостью, что и обычную; никогда не подписывать «на всякий случай»; не обнулять timelock на миграцию/изменение multisig или Security Council; мониторить заранее созданные durable-nonce-аккаунты и ожидающие подписи.

## Часть 4 — контрольные сценарии 2026 года (пункты 94–130)

> Эти номера и темы продолжают предоставленный пользователем набор сценариев. Ниже они нормализованы в классы угроз; конкретные даты, суммы, причинно-следственные связи и названия инцидентов не перепроверялись по первичным источникам. Перечень — контрольный список, не подтверждение того, что атака произошла или что контроль внедрён.

### X. Governance, цены и активы

94. [ ] **Захват governance/изменение полномочий** → вредоносное или скомпрометированное голосование меняет правила/authority. **Фикс:** проверяемый quorum, независимые подписанты, timelock, публичный diff, мониторинг предложений и возможность остановки по утверждённой процедуре. Watchtower не голосует и не управляет DAO.
95. [ ] **Манипуляция ценой через малоликвидный рынок/временное окно** → цена DEX не равна справедливой цене. **Фикс:** не использовать spot/один пул как settlement oracle; TWAP, глубина/ликвидность, предел отклонения и независимые источники; отказ от операции при расхождении.
96. [ ] **Wash trading/искусственный объём как сигнал цены или популярности** → метрики активности подделываются. **Фикс:** независимая проверка источников, фильтрация self-trade/Sybil по модели угроз, не выводить объём или «floor» как гарантированную стоимость.
97. [ ] **Подмена mint/токена/актива одноимённым или фальшивым** → символ и метаданные не доказывают адрес mint и полномочия. **Фикс:** allowlist точных mint/program IDs по cluster, проверка владельца/decimals/extensions/authority и отказ при неизвестном активе.

### Y. Ключи, signer и пользовательская поверхность

98. [ ] **Устаревшая программа, скомпрометированный upgrade authority или оставшийся ключ** → прежние полномочия действуют после смены версии/команды. **Фикс:** инвентарь адресов и authorities, verified builds, ограничение upgrade path, план ротации/отзыва и мониторинг изменений.
99. [ ] **Слабая энтропия в ключах/nonces** → угадываемые значения дают доступ или replay. **Фикс:** CSPRNG; `Math.random()` не применять к безопасности; тестировать источники случайности и отдельно документировать, если случайная величина только UI/test data.
100. [ ] **Утечка seed/private key/API secret в Git, логах, CI или workstation** → немедленная компрометация credential. **Фикс:** secret manager/KMS, least privilege, редактирование логов, secret scanning полной истории; считать обнаруженное в Git скомпрометированным и ротировать без печати значения.
101. [ ] **Signer/KMS с чрезмерными правами или доступный из игрового процесса** → компрометация сервиса превращается в перевод. **Фикс:** изолированный signer, раздельные identities, policy/лимиты на серверной границе, аппаратное/managed key custody, аудит и человеко-подтверждение значимых действий.
102. [ ] **Обход multisig/quorum или незащищённая замена подписантов** → один ключ фактически контролирует критичную операцию. **Фикс:** проверить реальные правила и программу multisig на целевом cluster; тестировать threshold, member rotation и timelock; не считать надпись «multisig» доказательством.
103. [ ] **Подмена frontend/build/update или ошибочный wallet UI** → пользователь подтверждает другой адрес, программу или сумму. **Фикс:** воспроизводимая/подписанная сборка, CSP/SRI где применимо, защита релизного pipeline и проверка DOM/параметров перед запросом подписи.
104. [ ] **Небезопасный UX подписания для игрока** → слепая подпись или неясное delegated approval. **Фикс:** показать сеть, программу, mint, recipient, сумму, fees и срок; запросить действие пользователя; не просить seed/private key; разрешать revoke и объяснять пределы разрешения.
105. [ ] **Компрометация рабочей станции/разработчика/подрядчика** → вредоносное расширение, remote support или похищенный сеанс открывают prod-доступ. **Фикс:** управляемые устройства, phishing-resistant MFA, разделение dev/prod, ограничение админских прав, проверка подрядчиков и процесс увольнения/отзыва доступа.
106. [ ] **Подмена зависимости/пакета/CI Action** → install/build исполняет код атакующего. **Фикс:** lockfile, reviewed upgrades, минимальные прямые зависимости, фиксированные Action SHAs, отказ от install scripts где возможно, dependency advisories и provenance.
107. [ ] **Вредоносный/преждевременный update или отсутствие окна проверки** → исправление само вводит backdoor/regression. **Фикс:** staged rollout, обязательный diff/review, тесты, pin/rollback и мониторинг; urgent patch не означает пропуск проверки подписи/источника.

### Z. Capability, нулевые значения и on-chain границы

108. [ ] **Бот/делегат получает больше полномочий, чем требуется** → автоматизация может переводить средства или менять настройки. **Фикс:** принцип наименьших прав, отдельный ключ, короткий срок, точный program/instruction/recipient allowlist, лимиты, rate limit и revoke.
109. [ ] **Обход adversarial guard/capability через fallback или альтернативный маршрут** → одна непроверенная ветка обходит основной authorization. **Фикс:** deny-by-default на каждой публичной инструкции, общая policy-функция, тесты негативных путей и запрет fallback к широкому разрешению.
110. [ ] **Ноль трактуется как «не задано/без ограничений»** → `0` обходит cap, fee, expiry или amount guard. **Фикс:** различать absent/null/zero, задать явную семантику нуля, проверять boundary `0`, `1`, max и переполнение; reject-closed для опасных параметров.
111. [ ] **Нет проверенного incident response** → задержка containment/ротации и потеря доказательств. **Фикс:** роли и контакты, порядок триажа, preservation, credential rotation, восстановление из проверенного build и post-incident review; не импровизировать ончейн-действия без полномочий.
112. [ ] **CPI/account substitution или произвольная target-программа** → корректная инструкция вызывается с чужими аккаунтами/программой. **Фикс:** проверка program ID, owner, signer, PDA seeds, writable privileges, ожидаемых accounts и контекста текущей/внешней инструкции; adversarial account-substitution tests.
113. [ ] **Слишком широкая/долго живущая session key** → компрометация временного ключа наносит неограниченный ущерб. **Фикс:** on-chain enforce scope/expiry/revoke, конкретный program + instruction discriminator, spend cap и ограниченный funding; проверять enforcement целевой программой, а не только registry/UI.
114. [ ] **Переполнение/округление/смешение единиц** → расчёты комиссии/баланса допускают обход границ. **Фикс:** checked arithmetic, точные integer units, валидированные decimals и property/fuzz tests для границ.
115. [ ] **Устаревшая версия программы, IDL или конфигурация cluster** → клиент/индексатор декодирует неверную инструкцию или отправляет не туда. **Фикс:** versioned IDL/config, binding program ID к cluster, совместимые миграции и блокировка неизвестной версии до review.
116. [ ] **Oracle завис/скомпрометирован/расходится с рынком** → stale либо единичный источник принимается за актуальный. **Фикс:** freshness/slot bounds, несколько независимых источников, deviation threshold и fail-closed; не заменять oracle operator-config ценой.
117. [ ] **DNS/домен/регистратор подменён** → frontend/RPC/релизный endpoint ведёт на атакующего. **Фикс:** MFA и hardware-backed доступ регистратора, защищённый DNS/records, мониторинг сертификатов и заранее проверенные official URL; DNSSEC полезен, но не заменяет контроль аккаунта.
118. [ ] **Нарушение treasury reserve/liabilities/recipient rules** → вывод превышает доступный баланс или уходит не тому адресату. **Фикс:** проверять баланс минус обязательства при постановке и исполнении, recipient binding, лимиты, timelock и независимое сверение accounting.
119. [ ] **Multisig/timelock существует только номинально или меняется «срочно»** → quorum не применяется к реальному пути либо delay обнулён. **Фикс:** проверить фактическую on-chain конфигурацию и CPI path; мониторить конфиг и очередь; emergency bypass имеет отдельное согласование и аудит.

### AA. Люди и инфраструктура

120. [ ] **Социальная инженерия сотрудника/контрагента или collusion** → доверенный доступ используется по ложному поручению. **Фикс:** callback по заранее известному каналу, dual control, независимая проверка платежных реквизитов/предложений и запрет срочных исключений из quorum только по сообщению.
121. [ ] **Компрометация хостинга, CI runner, контейнера или облачной identity** → злоумышленник меняет код/переменные или получает runtime access. **Фикс:** краткоживущие identity, изоляция окружений, least privilege, attestation/image digest, network egress controls, журналирование и регулярный restore/patch drill.
122. [ ] **Approval engine/автоматическое одобрение доверяет подменяемым данным** → неверное условие проходит без человека. **Фикс:** проверять входные данные из авторитетного источника, кворум/лимиты на стороне policy service, неизменяемый audit trail и независимый approval для значимых операций.
123. [ ] **Не применён upstream security patch или неподтверждён cherry-pick** → известная уязвимость остаётся либо вносится посторонний код. **Фикс:** отслеживать advisories, проверять источник/подпись upstream, тестировать diff и регистрировать версию/commit, исключения иметь ограниченный срок.
124. [ ] **Сестринский сервис/плагин/игровой компонент становится pivot** → общий токен, build pipeline или сеть переносит компрометацию в Watchtower/игру. **Фикс:** отдельные credentials, сетевые и release-границы, инвентарь интеграций и независимые проверки каждого компонента.
125. [ ] **AI-agent plugin/tool получает доступ к ключам или опасным действиям** → prompt/tool poisoning приводит к непроверенной подписи/деплою. **Фикс:** отключить доступ к signer, использовать read-only sandbox, ревью tool schema/version, deny-by-default capabilities, ручное подтверждение и тесты на отсутствие agent SDK/config в signer-процессе.
126. [ ] **Устаревший slot/time/локальные часы влияют на решение** → задержка/reorg или clock skew принимается за финальность/срок. **Фикс:** проверять slot/commitment/freshness и допустимое окно, синхронизировать часы; финансовое решение не основывать на одном timestamp или `confirmed`.
127. [ ] **RPC/indexer failover ведёт к неверному fork или неполному набору событий** → единичный upstream становится скрытым source of truth. **Фикс:** независимые provider comparison, slot/signature reconciliation, replay/backfill и сигнал расхождения; read-model не выдавать за консенсусный quorum.
128. [ ] **Неконтролируемое изменение/апгрейд программы** → новая версия меняет полномочия, layout или экономический инвариант. **Фикс:** upgrade authority под quorum/timelock, verified build, diff bytecode/IDL, staged activation, migration tests и мониторинг после апгрейда.
129. [ ] **Ложное governance/контрагентское подтверждение или подмена официального источника** → подписи собираются на неаутентичном proposal/адресе. **Фикс:** сверять proposal hash, адрес программы/получателя и channel of record; получать подтверждение независимым каналом, не из того же сообщения.
130. [ ] **Нет повторного аудита после релиза/инцидента/изменения полномочий** → контроль устаревает незаметно. **Фикс:** обязательный review после каждого существенного изменения кода, key/quorum, RPC, frontend или dependency; назначать владельца, критерии повторного аудита и проверяемое доказательство закрытия.
