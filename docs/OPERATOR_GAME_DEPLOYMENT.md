# Watchtower Operator — Руководство по продакшн-деплою

## Что это такое
Распределённый краудсорсинговый центр операторов, который позволяет любым пользователям (после подключения кошелька Solana) следить за реальным состоянием экосистемы игр Leo Games Studio в реальном времени, голосовать за разрешение инцидентов и помогать дежурной команде быстрее реагировать на проблемы.

## Ключевые инварианты безопасности (НИКОГДА не должны нарушаться)
1.  **Read-only по умолчанию:** Операторы никогда не получают прямого доступа к записи в блокчейн, игровые бэкенды, базы данных или конфигурации. Весь трафик голосов идёт только в отдельное хранилище модуля.
2.  **Никаких произвольных команд:** Операторы могут выбирать только из заранее утверждённого списка безопасных действий, прошедших аудит.
3.  **Консенсус прежде всего:** Ни одно действие не рассматривается к исполнению пока не наберёт требуемый процент взвешенных голосов (от 50% до 85% в зависимости от риска).
4.  **Человек в цикле:** Любые действия низкого, среднего и высокого риска ОБЯЗАТЕЛЬНО подтверждаются штатным сотрудником Leo Games с ролью STAFF перед исполнением. Действия высокого риска исполняют только люди.
5.  **Временной буфер:** После одобрения есть период ожидания (2–15 минут), за который сотрудник может отменить решение (`POST /api/operator/cancel`).
8.  **Хаб ничего не исполняет сам:** у Watchtower нет ключей, токенов инфраструктуры и доступа к мультисигу. Утверждённое решение уходит подписанным вебхуком исполнителю студии, см. «Исполнение решений».
6.  **Взвешенные голоса:** Вес голоса оператора зависит от его репутации и ранга. Новые игроки в роли наблюдателя имеют минимальный вес и не могут влиять на критические решения.
7.  **Защита от Сибилл:** Авторизация через кошелёк Solana предотвращает массовую накрутку мультиаккаунтами. История голосований и репутации отслеживается.

## Роли операторов
Роли открываются только прогрессом в играх студии, без платного входа. Полная модель: `docs/OPERATOR_SECURITY_FINAL.md`.

| Роль | Что может | Требования |
|---|---|---|
| Гость | только смотреть | нет |
| Кандидат | тренажёр, проверка правил | 10+ часов в одной игре, вход кошельком |
| Наблюдатель | голоса без риска и низкого риска | ранг 2+, 10+ часов, проверка правил сдана |
| Оператор | голоса до среднего риска | 2 игры, 100 репутации, точность 75%+ |
| Старший смены | все уровни риска и вето | 3 игры, 60+ дней, точность 85%+ |
| Хранитель | все уровни риска | 4 игры, 180+ дней, точность 90%+ |
| Сотрудник студии | подтверждение, отмена в буфер, отметка итога | назначается вручную |

Потолок веса голоса для не-сотрудников — 5. Необязательный возвратный стейкинг SOL только удваивает вес уже заслуженной роли и не открывает доступ.

## Уровни риска действий
| Уровень риска | Требуемый консенсус | Требует подтверждения сотрудника | Буфер перед исполнением | Примеры действий |
|---|---|---|---|---|
| Безопасный | 50% | Нет | 0 | Отметить ложный алерт, повысить приоритет |
| Низкий | 60% | Да | 2 мин | Обновить статус-страницу, включить CAPTCHA |
| Средний | 75% | Да | 5 мин | Усилить rate-limit, пауза кросс-игрового моста |
| Высокий | 85% | Только ручное исполнение | 15 мин | Пауза контракта через мультисиг |

Консенсус — это и доля, и минимальный вес голосов **за выбранное действие** (`consensusMinWeight`), а не общий вес всех голосов по инциденту.

Как исполняется каждое действие (`execution` в `allowedActions`):

| Действие | Риск | Исполнение |
|---|---|---|
| `mark_false_positive` | безопасный | `internal`: закрывается внутри хаба, внешние системы не затрагиваются |
| `increase_priority` | безопасный | `executor`: исполнитель студии будит дежурного |
| `notify_status_page` | низкий | `executor` |
| `enable_captcha` | низкий | `executor` |
| `disable_ingress` | средний | `executor` |
| `pause_bridge` | средний | `propose`: исполнитель только готовит предложение мультисигу, итог отмечает сотрудник |
| `pause_contract` | высокий | `propose` |

## Как запустить
Вахта открывается в основном интерфейсе (`/`), раздел «Вахта». API и собранный интерфейс отдаёт один процесс:
```
npm run build
NODE_ENV=production OPERATOR_SESSION_SECRET=... DATABASE_URL=... REDIS_URL=... npm start
```

### Переменные окружения
| Переменная | Обязательна | Что делает |
|---|---|---|
| `OPERATOR_SESSION_SECRET` | в продакшене | Ключ подписи сессий вахты, не короче 32 символов. Без него продакшен не стартует. В разработке создаётся случайный, и сессии сбрасываются при перезапуске. Смена ключа разлогинивает всех. |
| `DATABASE_URL` | нет | PostgreSQL для состояния вахты. Без неё состояние хранится в файлах `data/operator-game/` (или `OPERATOR_DATA_DIR`). |
| `DATABASE_SSL` | нет | `1` — TLS с проверкой сертификата, `no-verify` — TLS без проверки (только для управляемых БД с самоподписанным сертификатом). |
| `REDIS_URL` | при нескольких экземплярах | Redis 6.2+ для одноразовых кодов входа и лимитов. Без него они живут в памяти процесса. |
| `GAME_PROGRESS_SECRET_<ИГРА>` | для каждой подключённой игры | Секрет HMAC, которым игра подписывает отчёты о прогрессе, не короче 32 символов. |
| `GAME_PROGRESS_URL_<ИГРА>` | нет | Адрес API игры для опроса прогресса при входе игрока. |
| `GAME_PROGRESS_TOKEN_<ИГРА>` | нет | Bearer-токен для этого API. |
| `OPERATOR_EXECUTOR_URL` | нет | Адрес исполнителя студии для утверждённых решений, в продакшене только `https`. Без него решения ждут ручного исполнения сотрудником. |
| `OPERATOR_EXECUTOR_SECRET` | вместе с `OPERATOR_EXECUTOR_URL` | Секрет HMAC для вебхуков и колбэков итога, не короче 32 символов. Без него сервер с заданным адресом не стартует. |
| `OPERATOR_EXECUTOR_RETRY_MS` | нет | Паузы между попытками доставки, мс через запятую. По умолчанию 15 с, 30 с, 1, 2, 5, 10, 20, 30 мин (8 попыток). |
| `WATCHTOWER_ALLOW_DEMO` | нет | Демо-данные и демо-вход (`test_wallet`, `demo*`). В продакшене демо-вход выключен всегда, даже если флаг включён. |

`<ИГРА>`: `ARES1`, `AOF` (NeuroForge), `NEONRELAY`, `GUTTERCAPS`. Пакеты `pg` и `redis` стоят в `optionalDependencies` и подгружаются, только если заданы соответствующие адреса.

## Вход подписью кошелька
1. `POST /api/operator/nonce` `{ "wallet": "<адрес Solana>" }` возвращает `{ message, expiresAt }`. Сообщение содержит домен, адрес, одноразовый код и время. Код живёт 5 минут. Лимит: 20 запросов с IP и 8 на кошелёк за 10 минут, сверх лимита ответ 429 с `retry-after`.
2. Кошелёк подписывает сообщение (`signMessage`, ed25519). Это не транзакция: ничего не списывается.
3. `POST /api/operator/auth` `{ "wallet", "signature": "<base58>" }`. Сервер забирает код один раз (Redis `GETDEL`), поэтому повтор той же подписи или вторая попытка с тем же кодом дают `401 login_code_expired`. Неверная подпись: `401 bad_signature`, запись в аудит.
4. Ответ: `{ player, token, expiresAt, mode }`. Сессия действует 12 часов. Действия (`/api/operator/exam`, `/vote`, `/approve`) принимают её только в заголовке `x-operator-session` (`Authorization` может быть занят read-токеном API). Кошелёк берётся из сессии: без сессии `401 session_required`, чужой `wallet` в теле `403 wallet_mismatch`.

## Прогресс из игр
Ранги вахты открываются только реальными часами и рангами в играх. Демо-прогресс получают лишь демо-кошельки в разработке. У настоящего адреса без отчётов игр прогресс нулевой, профиль показывает `progressSource: "none"`.

**Отправка игрой (push).** `POST /api/games/progress`:
```
x-watchtower-game: ares1
x-watchtower-timestamp: 1791216000000          (мс, допуск ±5 минут)
x-watchtower-signature: sha256=<hex HMAC-SHA256(secret, "<timestamp>.<сырое тело>")>

{ "reports": [ { "wallet": "<адрес>", "hours": 37.5, "rank": 3, "updatedAt": 1791216000000 } ] }
```
Необязательное поле `ref` — код партнёрского приглашения (`[A-Z0-9]{4,16}`, иначе отчёт отклоняется с `bad_ref`). Игра передаёт его, если игрок пришёл по ссылке `?ref=<код>`; засчитывается только для новичка, подробности в [PARTNER_PROGRAM_PILOT.md](PARTNER_PROGRAM_PILOT.md). До 500 отчётов за запрос, 600 запросов в минуту на игру. Отчёт со старым `updatedAt` не перетирает более свежий: ответ считает его в `stale`. Ответ: `{ accepted, stale, rejected: [{ index, reason }] }`.

**Опрос игры (pull).** Если задан `GAME_PROGRESS_URL_<ИГРА>`, при входе сервер делает `GET <url>?wallet=<адрес>` (таймаут 3 с, без редиректов) и ждёт `{ "hours", "rank", "updatedAt"? }`. Ответ 404 значит «игрок неизвестен». Ошибка игры не мешает входу: остаются последние сохранённые данные.

Вахта только читает прогресс и ничего не пишет в игры.

## Исполнение решений
Хаб не исполняет решения сам. После голосования решение проходит этапы:

```
open/voting → consensus_pending ─ сотрудник ─→ approved ─ буфер ─→ handed_off ─→ executed
                │ безопасные: сразу approved      │ отмена            │       └─→ execution_failed
                └─→ rejected                      └─→ cancelled       └ итог: колбэк исполнителя или сотрудник
```

**Вебхук исполнителю.** Когда буфер истёк, сервер отправляет `POST <OPERATOR_EXECUTOR_URL>` (таймаут 5 с, без редиректов):
```
x-watchtower-timestamp: 1791216000000
x-watchtower-signature: sha256=<hex HMAC-SHA256(OPERATOR_EXECUTOR_SECRET, "<timestamp>.<сырое тело>")>
x-watchtower-delivery:  <deliveryId>

{ "deliveryId", "attempt": 1, "sentAt", "mode": "execute" | "propose",
  "incident": { "id", "game", "title", "severity", "detectedAt" },
  "action": { "id", "title", "riskLevel" },
  "decision": { "share", "weight", "voters", "staffApproved", "approvedAt", "scheduledFor" },
  "callbackPath": "/api/operator/executor/result" }
```
- `deliveryId` одинаков для всех попыток по одному решению. Исполнитель обязан по нему отбрасывать повторы.
- `mode: "propose"`: ничего не исполнять, только подготовить предложение (например, транзакцию мультисига на подпись людям).
- Ответ `2xx` с пустым телом или `{ "status": "accepted" }` значит, что решение принято и итог придёт колбэком. Можно сразу ответить `{ "status": "executed" | "failed" | "proposed", "detail": "..." }`.
- Не `2xx`, таймаут или неверный ответ ведут к повтору по `OPERATOR_EXECUTOR_RETRY_MS`. После последней попытки доставка помечается `undelivered`, и решение ждёт сотрудника: он выполняет вручную или отправляет снова.

**Итог от исполнителя.** `POST /api/operator/executor/result` с теми же заголовками `x-watchtower-timestamp` и `x-watchtower-signature` (секрет исполнителя, допуск ±5 минут), тело `{ "deliveryId", "status": "accepted" | "proposed" | "executed" | "failed", "detail"? }`. Ответы: `200` (повтор после итога даёт `already: true`), `401` при неверной подписи или старой метке времени, `403 executor_not_connected`, `404 unknown_delivery`, `400 bad_status`. Для `mode: "propose"` статус `executed` отклоняется с `409 manual_confirmation_required`: итог действий через мультисиг отмечает сотрудник.

**Сотрудник.** `POST /api/operator/cancel { incidentId }` отменяет решение, пока не истёк буфер (перезарядка действия снимается). `POST /api/operator/resolve { incidentId, result: "executed" | "failed" | "retry", note? }` отмечает итог переданного решения; `retry` снова отправляет решение, если доставка не удалась. Не сотрудник получает `403`, неподходящий этап — `409`.

**Репутация.** Начисляется только при `executed`. Сбой исполнения и отмена сотрудником репутацию не меняют: это не ошибка голосовавших.

**Несколько экземпляров.** Экземпляр «забирает» решение под общей блокировкой (`claimUntil`, 15 с) и отправляет его вне блокировки, поэтому одно решение уходит один раз. Если экземпляр упал посреди отправки, решение подберёт другой после `claimUntil`. Решения, чей буфер истёк, пока сервер стоял, передаются сразу после старта. Это проверяет `scripts/operator-execution.test.mjs`.

## API эндпоинты
- `GET /api/operator/state`: инциденты, лидерборд, смена, разрешённые действия, `auth` (нужна ли подпись, доступен ли демо-вход), `progressSources` (какие игры подключены).
- `POST /api/operator/nonce`, `POST /api/operator/auth`: вход, см. выше.
- `GET /api/operator/player/<wallet>`: публичный профиль, `progressSource`: `game` / `demo` / `none`.
- `GET|POST /api/operator/exam`: проверка знания правил (POST требует сессию).
- `POST /api/operator/vote`, `POST /api/operator/approve`: голос и подтверждение сотрудником (требуют сессию).
- `POST /api/operator/cancel`, `POST /api/operator/resolve`: отмена в буфер и итог исполнения (сотрудник, требуют сессию).
- `POST /api/operator/executor/result`: итог от исполнителя студии (подпись HMAC).
- `GET /api/operator/journal?limit=100`: журнал вахты — голоса, консенсус, подтверждения, отмены, доставка и итог; кошельки укорочены.
- `POST /api/games/progress`: отчёты игр.
- `GET /r/<код>`, `GET /api/partners/rules|me|review`, `POST /api/partners/join|claim|decide`: партнёрская программа, см. [PARTNER_PROGRAM_PILOT.md](PARTNER_PROGRAM_PILOT.md).

## Хранение данных
Разделы состояния: `players`, `incidents`, `ratelimits`, `cooldowns`, `reputation-log`, `executed`, `shift`, `game-progress`, `journal` (последние 1000 записей журнала вахты).
- **Файлы** (по умолчанию): `data/operator-game/<раздел>.json`, атомарная запись.
- **PostgreSQL** (`DATABASE_URL`): таблица `watchtower_state(name text primary key, data jsonb, version bigint, updated_at timestamptz)` создаётся автоматически. Если таблица пуста, а файлы есть, данные переносятся из файлов при первом старте (`storage_migrated_from_files` в логе).
- **Redis** (`REDIS_URL`): одноразовые коды входа и лимиты входа общие для всех экземпляров, ключи с префиксом `wt:`.

### Несколько экземпляров API
Экземпляров может быть сколько угодно за любым балансировщиком, привязка сессий к экземпляру не нужна.
- **Запись.** Каждое изменение (вход, голос, проверка правил, подтверждение, отчёт игры, фоновые задачи) — одна транзакция PostgreSQL под общей блокировкой `pg_advisory_xact_lock`. Внутри неё экземпляр сначала перечитывает разделы, которые изменил кто-то другой (по `version`), затем применяет изменение и сохраняет разделы с `version + 1`. Одновременные голоса по одному инциденту с разных экземпляров не теряются; это проверяет тест `несколько экземпляров на одной базе`.
- **Чтение** идёт из памяти. О чужих записях экземпляр узнаёт через `LISTEN/NOTIFY` (канал `watchtower_state`, обычно за миллисекунды) и дополнительно опрашивает версии раз в 5 секунд, если уведомления потерялись.
- **Отказ базы.** Если записать не удалось, ответ `503 storage_unavailable`: голос не считается принятым, и интерфейс просит повторить позже. В `/api/readyz` проверка `operator` становится `ok: false`, и балансировщик снимает экземпляр с трафика. После восстановления базы статус возвращается сам.
- **Пропускная способность.** Записи вахты выполняются по одной на кластер: несколько миллисекунд на голос. Этого хватает с большим запасом, потому что голосов не больше 12 в час на оператора. Опрос API игр при входе идёт вне блокировки.
- **Одновременный старт.** Создание таблицы и перенос данных из файлов идут под той же блокировкой, поэтому экземпляры можно выкатывать одновременно на пустую базу. Раньше параллельный `CREATE TABLE IF NOT EXISTS` ронял примерно половину стартов (`pg_type_typname_nsp_index`). Это проверяет тест `одновременный старт экземпляров на пустой базе`.
- **Без `DATABASE_URL`** (файлы) экземпляр должен быть один.

## Мониторинг и лимиты
- Автоматическая ротация старших операторов каждый час по топ-5 по репутации
- Истечение инцидентов через 10 минут если по ним не было голосов
- Максимальный уровень репутации не ограничен, но вес голоса имеет логарифмическое затухание после 5000 очков
- Голоса, решения и исполнение пишутся в журнал вахты (`GET /api/operator/journal`); отклонённые подписи колбэков — в общий аудит-лог (`/api/audit`)

## Награды для лучших операторов
- За решение, исполнение которого подтверждено, начисляется репутация (5 очков базово, пропорционально рангу)
- За голос против исполненного решения снимается 1 очко репутации; за отклонённое сотрудником решение — 1 очко у голосовавших за него
- Сбой исполнения и отмена в буфер репутацию не меняют
- Лучшие операторы месяца получают реальные награды от студии: NFT, токены, внутриигровые предметы, мерч, доступ к закрытому чату с разработчиками
- Предотвращение реального критического инцидента (эксплойт, утечка) дополнительно вознаграждается из баунти-фонда студии.
