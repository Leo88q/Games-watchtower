# Максимум: целевое состояние экосистемы и «тёплый продукт»

Дополнение к `docs/ECOSYSTEM_MINIMUM_REQUIREMENTS.md`. Минимум отвечает на вопрос
«что нужно, чтобы игра вообще была в экосистеме»; максимум — на вопрос
**«что нужно, чтобы экосистема была переплетена и продукт был тёплым»**:
live-данные, сквозные пользовательские сценарии, контракты-инварианты, бэкенд с SLO и фронтенд,
которым можно пользоваться каждый день без «а это у нас mock».

Машинночитаемая версия требований — `docs/ecosystem-target.spec.json`
(73 требования: contracts 12, backend 18, frontend 13, data 8, ops 10, interweaving 12;
у каждого — уровень L2/L3/L4 и доказательство). Проверка покрытия:
`node scripts/check-ecosystem-target.mjs` (и `--strict` для CI).

## 0. Лестница зрелости: что такое «тёплое состояние»

| Уровень | Название | Признак | Данные | Что можно делать |
|---|---|---|---|---|
| **L0** | cold | репозиторий без интеграции | нет | ничего |
| **L1** | passport | паспорт и адаптер заявлены | нет или mock | нельзя публиковать наружу |
| **L2** | connected | read-only экспортер отдаёт факты, хаб видит tenant, `dataQuality` честный | реальные, свежие | внутренние дашборды |
| **L3** | **warm** | полный контур метрик/экономики/идентичности, инварианты и алерты работают, cross-game связки включены | live, ≤5 мин свежесть | решения по игре, эксперименты, инвесторские отчёты |
| **L4** | hot | SLO соблюдаются, proposal-flow в бою, DR и дежурство проверены, студийная экономика консолидирована | live + консолидированные | масштабирование, кросс-чейн, ML-автоматизация с approval |

Сегодня (2026-09-23) экосистема находится на **L1**: `GET /api/ingestion/adapters` → `configured: 0 из 5`,
провайдер `mock`. Тёплый продукт — это устойчивое L3 по всем пяти tenant'ам и L4 хотя бы по одному.

## 1. Плоскость «Контракты» — максимум

1. **Реестр адресов** как единый источник: программы, mint, treasury, PDA, мультисиг — подтверждены
   сетью (RPC), опубликованы в паспорте игры и в ENV хаба; тест консистентности. Сейчас: у ares1
   `last_verified_at = null`, у neonrelay — placeholder'ы, у aof — смесь реального и placeholder.
2. **IDL-driven разработка**: IDL публикуется, версия синхронизируется (`sync-idl.mjs`), doc-drift guard
   роняет CI при расхождении паспорта и кода.
3. **Безопасность аккаунтов до нуля**: owner-констрейнты и проверки владельца (SW002 — 70 находок
   в guttercaps), валидация PDA seeds (SW013 — 54), `token::authority`/`token::mint` (SW009/010),
   защита от деления на ноль (SW024 — 20), `init` вместо `init_if_needed` там, где это корректно,
   `reload()` после CPI, `emit!` на каждое изменение состояния (без этого хаб слеп).
4. **Инварианты как property-тесты, а не как текст**: сохранение ценности (mint − burn = net),
   невозможность двойного claim, соблюдение caps и эпох, solvency escrow, отсутствие отрицательных
   балансов, sanity оракула (staleness/confidence), проверка пределов слippage.
5. **Session keys как продукт**: scope-deny (`withdraw_treasury`), лимит 0.01 SOL, expiry, revoke,
   allowlist программ — и всё это с тестом, который падает при попытке запрещённой операции.
6. **Custody и апгрейды**: upgrade authority = мультисиг + timelock (без single-key), регламент
   emergency pause, план миграции состояния, версионирование программ.
7. **Devnet → mainnet гейт** (только решение оператора): аудит пройден, инварианты зелёные,
   мониторинг и rollback на месте, никаких хардкод-mint и «throwaway» аккаунтов в прод-пути.

## 2. Плоскость «Бэкенд» — максимум

1. **Ingestion промышленного класса**: LaserStream gRPC (failover, 24h replay) + Shyft gPA/webhooks
   + DAS; отслеживание commitment и finalized lag; обработка реоргов/откатов с компенсацией проекций;
   gap detection и healing только полным backfill.
2. **Read-model, который можно пересобрать**: PostgreSQL с RLS по `tenant_id`, TimescaleDB для
   временных рядов, Redis для кэша/лимитов/очередей, материализованные представления (в т.ч. кросс-игровые),
   команда rebuild и сверка проекций с первичными событиями.
3. **Экономический ledger двойной записи**: mint/burn, sources/sinks, комиссии, treasury, отчёт
   сверки «события ↔ проводки ↔ балансы» — без него экономика не управляема.
4. **Reward pipeline**: caps по дням/матчам, эпохи, Merkle-запечатывание, claim intents/confirmations,
   доказанное отсутствие двойной выплаты.
5. **Anti-fraud и KYT**: risk scoring кошелька, Sybil/multi-account, аномальные reward-паттерны,
   скрининг адресов; с precision/recall на исторических метках и журналом решений (ложные
   срабатывания измеряются, а не обсуждаются).
6. **API как продукт**: версионирование, OpenAPI-спека, пагинация, ETag/кэш, единый контракт
   ошибок, request-id, read-токены с ротацией и constant-time сравнением (как уже сделано в trafficgen).
7. **Proposal-контур через границу систем**: хаб отправляет подписанное предложение → игра
   подтверждает локально (RBAC + 2FA + второе подтверждение) → применяет → пишет в оба audit-журнала →
   умеет откатить. Ни одного прямого write из хаба.
8. **Наблюдаемость**: OTel-трейсы сквозь ingest→проекция→API, Prometheus, структурированные логи,
   Sentry, SLO-дашборд на игру.
9. **Надёжность**: retry с backoff, circuit breaker, dead-letter, keyset-пагинация, DR с RPO ≤ 15 мин
   и RTO ≤ 4 ч, регулярный проверенный restore, нагрузочные тесты.
10. **Секреты и custody**: vault/KMS, разделение ключей подписанта и сервиса, отсутствие signer
    в экспортере, gitleaks/scan_secrets в CI.

## 3. Плоскость «Фронтенд» — максимум

1. **Честность как UX**: бейдж `dataQuality` на каждом виджете; отсутствующее — `unavailable` с причиной,
   никогда нулём; трассируемость по клику — формула, источник, период агрегации, часовой пояс,
   `lastVerifiedAt`.
2. **19 панелей управления в хабе** (`src/os/control-panels-v3.js`) читают реальные API-поля и
   показывают: статус, конфиг, метрики, действия (read/proposal), ссылки на SDK и доки. Сейчас это
   карта стека; в тёплом состоянии — рабочие панели с живыми данными.
3. **Экосистемный экран** на `/api/ecosystem/status`: по каждому tenant'у `stage, dataQuality,
   lastVerifiedAt, findings{critical,high}, connected, L-уровень`, покрытие относительно
   `docs/ecosystem-target.spec.json`.
4. **Игровые сценарии**: онбординг кошелька guest → embedded → native → linked без потери прогресса;
   session keys с действиями без попапов и понятными отказами; инвентарь cNFT/Standard с provenance;
   маркетплейс с честными статусами финализации сделки.
5. **Proposal-flow UI**: 2FA, второе подтверждение, таймер, дифф эффекта, audit trail, кнопка отката —
   опасное действие физически невозможно выполнить одним кликом.
6. **Realtime и деградация**: WebSocket/SSE для алертов и live-метрик, автоматический откат на polling.
7. **Доступность, локализация, производительность**: ru/en, клавиатурная навигация, aria в критичных
   потоках; LCP < 2.5 c, bundle < 200 kB gzip; skeleton/retry/error boundary и честные пустые состояния.

## 4. Переплетение: 12 контуров, которые делают экосистему единой

| # | Контур | Что конкретно связывает игры | Готово, когда |
|---|---|---|---|
| 1 | **Идентичность** | один `studio_profile` PDA, одинаковый `playerKey`, linked wallets | один игрок находится по `playerKey` в 2+ играх |
| 2 | **Согласия** | единый consent/opt-out, действующий во всех играх и каналах | opt-out немедленно блокирует доставку везде |
| 3 | **Инвентарь** | cross-game контракт переноса активов, лимиты, nullifier от дублей | предмет реально переносится между играми с аудит-логом |
| 4 | **Provenance** | `source_game`, `asset_id`, история переходов | по активу виден путь между играми |
| 5 | **Экономика** | studio treasury, per-game budgets, запрет автономной эмиссии | сводный ledger сходится по консолидации |
| 6 | **Сезоны и события** | общий календарь, кросс-игровые квесты, единые награды | событие засчитано в 2+ играх |
| 7 | **Профиль игрока** | уровень, достижения, статус трактуются одинаково | профиль читается из хаба во всех играх |
| 8 | **Кампании** | сегменты по анонимным группам, consent/frequency/budget, attribution, rollback | кампания прошла сквозной прогон с атрибуцией и откатом |
| 9 | **Аналитика** | единые определения метрик, общий funnel, cross-game retention, whale radar | cross-game отчёт с общими метриками |
| 10 | **Алерты и инциденты** | один severity-словарь, SLA, эскалация, единый audit log | алерт виден и в хабе, и в игре |
| 11 | **Контроль** | подписанный proposal → подтверждение в игре → два журнала | сквозной тест proposal без write из хаба |
| 12 | **Кросс-чейн** | RACE/idosgames с лимитами, антифродом, KYT | перенос ценности с проверкой лимитов |

## 5. Разделение ответственности: игра vs хаб (без дублирования)

| Область | Игра (tenant) | Хаб |
|---|---|---|
| Факты о себе | источник истины, локальные инварианты, экспортер | только чтение |
| Ключи | свои signer'ы, мультисиг, custody | **никогда** никаких приватных ключей и signer'ов |
| События | эмиссия + нормализация в envelope | приём, дедупликация, канонический словарь, проекции |
| Экономика | локальный ledger + сверка | консолидация, лимиты, студийная treasury-политика |
| Активы | владение, mint/burn, инвентарь | cross-game правила, provenance, агрегация |
| Контроль | локальное подтверждение и исполнение | предложения, RBAC-модель, аудит, отчёты |
| Аналитика | игровые метрики и события | сквозная аналитика, cross-game, ML-фичи, инвесторские срезы |
| Фронтенд | игровые экраны, кошелёк, session keys | дашборд, 19 панелей, экосистемный экран, control UI |

## 6. Измеримые врата «тёплого состояния» (проверяются автоматически)

```text
[ ] 14/14 обязательных /watchtower/* маршрутов отвечают; health.writes = false
[ ] finalized lag p95 ≤ 30 c; свежесть данных ≤ 5 мин; uptime ≥ 99.9%/мес
[ ] API read p95 ≤ 300 мс; ingest p99 ≤ 2 с; exporter availability ≥ 99.9%
[ ] 0 открытых critical/high findings либо formal accepted-risk с обоснованием и владельцем
[ ] CI зелёный на каждом PR: сборка, тесты, secret-scan (0), doc-drift, аудит
[ ] Инварианты экономики покрыты property-тестами и проходят на каждом релизе
[ ] DR: RPO ≤ 15 мин, RTO ≤ 4 ч, restore проверен; алерты p1 ≤ 5 мин, p2 ≤ 30 мин
[ ] Proposal-flow протестирован сквозным тестом: proposal → approval → apply → rollback
[ ] Cross-game контуры: игрок найден в 2+ играх, перенос актива выполнен, кампания с атрибуцией
[ ] Публичные отчёты (инвесторские, студийные) не содержат mock и указывают подключённые tenant'ы
[ ] Покрытие экосистемы: ≥ 80% tenant'ов на L3+ (считает scripts/check-ecosystem-target.mjs --strict)
```

## 7. Что не делается даже на максимуме

- Приватные ключи, seed-фразы, upgrade authority и signer'ы — **никогда** в хабе и никогда в отчётах.
- Ни одного блокчейн-write из хаба; только proposal + человеческое подтверждение в игре.
- Ни одной автоматической выплаты, блокировки игрока или рассылки без approval, audit log и rollback.
- Никаких выдуманных метрик, «нарисованных» графиков и mock в публичных документах.
- Никакого mainnet-деплоя без пройденного аудита, зелёных инвариантов и плана отката.

## 9. Как проверить текущее состояние и прогресс

```bash
node server/index.js &                                   # хаб, порт 8787
node scripts/check-ecosystem-target.mjs                  # уровни по tenant'ам и покрытие
node scripts/check-ecosystem-target.mjs --strict         # гейт для CI (цель — 80% на L3+)
curl -s localhost:8787/api/ingestion/adapters            # configured / quality по адаптерам
curl -s localhost:8787/api/ecosystem/status              # появится в результате промпта хаба
```

Требования по каждой позиции и доказательства — в `docs/ecosystem-target.spec.json`;
формулировки задач для игр — в `prompts/arena/PROMPT_ARENA_*.md`.
