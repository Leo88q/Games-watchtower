03 / THE STUDIO AND ITS SYSTEM

First, we build games.
Watchtower helps us understand them.

Watchtower is not a game token or an “autopilot” promise. It is Leo Games Studio’s in-house operating system: it receives game events, builds analytics scoped to a specific title and region, reports data quality and helps the team investigate signals.

A

Game events
Funnels and time slices are built from incoming events, not polished demo numbers.

B

Economy and health
The code contains 40 metric definitions across 8 families. A value appears only when its required inputs exist.

C

Player safety
Watchtower is designed as a read-only hub: it does not hold a player’s keys or sign transactions for them.

Status, plainly: the analytics core and interface exist. Production event streams and each game connection must be verified separately; we cannot claim that all four games are fully connected to live telemetry today.

04 / WHY US

Why call this
the first real solution for a game studio?

Not because analytics, anti-cheat or game platforms do not exist. Our thesis is more specific: one game studio is building its own games and, at the same time, a verifiable system it needs to operate them.

01

OUR OWN GAMES FIRST

Built from production needs

Watchtower is designed around Leo Games Studio’s actual portfolio: different genres, event schemas and release stages—not an abstract template made for a pitch deck.

02

ONE OPERATING LOOP

See the whole game journey

Events, funnels, economy, regions and safety signals share the same game context. That lets a studio examine changes from first visit to a return session.

03

HONEST SIGNALS

No event means no invented zero

Every metric has quality and a source. Unknown stays unavailable, partial stays partial, and separate game streams are not blended into one flattering number.

04

PLAYERS KEEP CONTROL

Observing is not owning

The hub has no signing keys and cannot sign a player’s transaction. Risky on-chain actions must never become an automatic decision made by analytics.

06 / HOW THE STUDIO WILL GROW

No invented dates.
Release gates instead.

First prove the system on one game. Then repeat it for the rest. Each next stage starts only after the previous one passes its checks.

PHASE 01 · NOW

Make the game worth returning to

Refine core loops, onboarding and the first playtests. Collect only the events that help improve the game.

Gate: an understandable build, a working loop and known limitations.
PHASE 02 · CONNECT

Connect real telemetry

Add adapters one game at a time, agree on event schemas, freshness and deletion; test each title and region separately.

Gate: end-to-end events are verified; missing and duplicate data are visible.
PHASE 03 · OPERATE

Open reliable game tests

Improve analytics, anomaly signals, player support and human incident review. Any access restriction needs a clear reason.

Gate: safety, rules, support and monitoring are ready for an audience.
PHASE 04 · CONNECT WORLDS

Link games only when it helps

Explore shared achievements, an optional profile and Studio API after standalone games prove their value and players understand the rules.

Gate: clear player benefit, consent, checked contracts and a real way not to take part.

No made-up completion percentages. We publish dates when a phase has an owner, dependencies and release criteria. Calendar time alone does not move a feature to the next stage.
